八、★★★ 轮次66：加 Vulkan 后端 + armv8.2 指令集（**照这一节做**）
----------------------------------------------------------------

### 8.1 指令集（便宜、低风险、必做）

原来没设任何 `-march`，走 NDK 默认的 **armv8-a** 基线 —— 量化矩阵乘最吃的
**dotprod / fp16** 全没开。现在加：

```
-DGGML_CPU_ARM_ARCH=armv8.2-a+dotprod+fp16
```

* 变量名就是新版 llama.cpp 的 **`GGML_CPU_ARM_ARCH`**
  （旧的 `LLAMA_CPU_ARM_ARCH` 已经不存在；ggml/CMakeLists.txt:184、ggml/src/ggml-cpu/CMakeLists.txt:210）。
* ★ **为什么不上 i8mm**：i8mm 要 `armv8.6-a`，只有较新的 CPU 有；
  本工程没有做"多版本 .so + 运行时挑"（那要 `GGML_CPU_ALL_VARIANTS=ON` + `GGML_BACKEND_DL=ON`，
  而 BACKEND_DL 在 Android 上找不到后端目录，见 8.4）。
  写进 `-march` 就会在**老设备上直接 SIGILL 崩**。**稳的底线就是 dotprod + fp16。**
* `-O3` 不用加：`CMAKE_BUILD_TYPE=Release` 本来就带 `-O3 -DNDEBUG`（实测编译命令行里有）。
* ★ 真机验证（`llama_print_system_info()`，现在会打进 logcat）：
  `CPU : NEON = 1 | ARM_FMA = 1 | FP16_VA = 1 | DOTPROD = 1 | LLAMAFILE = 1 | REPACK = 1 |`

### 8.2 Vulkan 后端：不用下 Vulkan SDK，但要三样东西

`-DGGML_VULKAN=ON`（开关名确认过：ggml/CMakeLists.txt:224）。

| 需要什么 | 从哪来 | 怎么接 |
|---|---|---|
| `glslc`（着色器编译器） | ★ **NDK 自带**：`<NDK>/shader-tools/windows-x86_64/glslc.exe`（shaderc v2022.3 / ndk-r26c） | `-DVulkan_GLSLC_EXECUTABLE=<那个路径>` |
| Vulkan **C 头** + `libvulkan.so` stub | ★ NDK sysroot：`usr/include/vulkan/`（含 `vulkan_core.h`）、`usr/lib/aarch64-linux-android/24/libvulkan.so` | 不用管，CMake 的 FindVulkan 在 ANDROID 上自动找到（实测报 `found version "1.3.275"`） |
| `vulkan.hpp`（C++ 绑定） | ★★ **NDK 里没有** | 从 `ghproxy.net` 下 `KhronosGroup/Vulkan-Headers` 的 **v1.3.275** tag，只把 `*.hpp` 拷到 `D:\spirv_headers\install\include\vulkan\`（**不要拷 `.h`**，那些留给 NDK sysroot） |
| `SPIRV-Headers`（CMake 要 `find_package(... CONFIG REQUIRED)`） | `ghproxy.net` 下 `KhronosGroup/SPIRV-Headers` | 手写一个最小 `SPIRV-HeadersConfig.cmake` 放到 `D:\spirv_headers\install\share\cmake\SPIRV-Headers\` |
| **host 编译器**（着色器生成工具 `vulkan-shaders-gen` 是跑在 PC 上的宿主程序） | ★★ 本机有 **Visual Studio 2026 Build Tools**（`C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools`） | 整个构建要在 **vcvars64 环境里**跑：`cmd /c "call vcvars64.bat && cmake ... && cmake --build ..."` |

★ `vulkan.hpp` 的 include 路径靠 **`CPLUS_INCLUDE_PATH` 环境变量**给（比塞 `-DCMAKE_CXX_FLAGS`
安全：后者会顶掉 NDK toolchain 的 `CMAKE_CXX_FLAGS_INIT`，实测会丢 `-fPIC` 一类东西）。

★ 实测 glslc 太老 ⇒ 这些着色器扩展**一律被探测为不支持**（CMake 会打印
`GL_KHR_cooperative_matrix not supported by glslc` 等 7 行）：
coopmat / coopmat2 / integer_dot / bfloat16 / e2m1 / e4m3。
**这不是错误**，是 `test_shader_extension_support()` 的正常降级路径；
但**很可能正是真机上 Adreno 拒绝 pipeline 的原因**（见第八节末尾）。

### 8.3 编译命令（实测可用）

`build/_r66/build_vulkan.bat` 是这一轮实际用的脚本，核心就是原来的参数 +
`-DGGML_VULKAN=ON`、`-DGGML_CPU_ARM_ARCH=armv8.2-a+dotprod+fp16`、
`-DSPIRV-Headers_DIR=...`、`-DVulkan_GLSLC_EXECUTABLE=...`，
外面套一层 `call vcvars64.bat`，并设 `CPLUS_INCLUDE_PATH=D:\spirv_headers\install\include`。

### 8.4 ★★ 为什么**不能**用 `GGML_BACKEND_DL=ON` 来做"优雅回退"

看起来 `GGML_BACKEND_DL=ON` 能让后端变成运行时 dlopen、加载失败也不致命，
但它在 Android 上**找不到后端**：`ggml_backend_load_best()` 的搜索路径是
`get_executable_path()`（`/proc/self/exe` → **`/system/bin/app_process64`**）与 cwd，
而不是 App 的 nativeLibraryDir ⇒ 会一个后端都加载不到。
本工程继续用 **`GGML_BACKEND_DL=OFF`**，回退靠第九节的设备探测 + 异常兜底。

九、★★★ 轮次66 真机上走的三个坑（**每一个都能让提速静默归零，全都不报错**）
--------------------------------------------------------------------------------

设备：小米 2210132C（Xiaomi 13 / **骁龙 8 Gen 2 / Adreno 740** / 安卓 SDK 37）。
模型：**Qwen2.5-1.5B-Instruct Q4_K_M（1.06 GB，28 层）**。

**坑 ①：`n_gpu_layers` 写死 0。**
原来的 JNI 里是 `mp.n_gpu_layers = 0;` —— 就算把 Vulkan 编出来，
层也永远留在 CPU 上（GPU 编了白编）。现在由 Java 侧按「⚡ GPU 加速」开关传进来。

**坑 ②：只认 `GGML_BACKEND_DEVICE_TYPE_GPU`，而手机 GPU 全是 `IGPU`。**
第一版 `device_is_gpu()` 写的是 `type == GGML_BACKEND_DEVICE_TYPE_GPU`，
真机上打出：
```
★★ 后端设备：Vulkan0(Adreno (TM) 740, 显存 11446/11446 MB); CPU(CPU, ...)
  ⇒ **一个 GPU 设备都没有，自动回退 CPU**
```
设备明明在清单里，却被数成 0 个。`ggml-backend.h` 的枚举是
**CPU=0 / GPU=1（独立显存）/ IGPU=2（集显）**，手机 GPU 全走 IGPU
⇒ 现在判据是 `GPU || IGPU`。

**坑 ③（最隐蔽，而且害的是 CPU 那条路）：装上 Vulkan 后端之后，llama.cpp 会把整个模型的 mmap 关掉。**
`src/llama-model.cpp:1576`：
```cpp
if (ml.use_mmap && params.load_mode == LLAMA_LOAD_MODE_AUTO) {
    for (dev : devices) if (!props.caps.mmap_support) { ml.use_mmap = false; break; }
}
```
而 `ggml/src/ggml-vulkan/ggml-vulkan.cpp:15425` 上报的是
`/* .mmap_support = */ !ctx->is_integrated_gpu` —— **手机集显 = false**。
⇒ 只要 Vulkan 设备进了 `devices`（哪怕 `n_gpu_layers = 0`），
**1 GB 权重就被 read() 进匿名内存**（日志里那行 `load_mode = none` 就是它），
在 Android 上直接被压进 zram 反复换进换出。
⇒ 修法：显式写 **`mp.load_mode = LLAMA_LOAD_MODE_MMAP;`**（不是 AUTO，AUTO 才会走那段降级）。
★ 实测代价量级：换页/带宽瓶颈下 decode ~7 s/token。

**★ 坑 ④（本轮的诚实结论）：Adreno 740 驱动拒绝这批着色器。**
补上 ② 之后 Vulkan 真的用上了（`load_tensors: offloaded 29/29 layers to GPU`，
`sched_reserve: graph: nodes = 961, splits = 3`），
但**第一次 `llama_decode` 就抛**：
```
Abort message: 'terminating due to uncaught exception of type vk::UnknownError:
                 vk::Device::createComputePipeline: ErrorUnknown'
```
`ggml-vulkan.cpp:772` 的 `createComputePipeline` **外面没有 try/catch**
（同文件的 `createShaderModule` 有），异常穿过 `llama_decode` → `std::terminate` → **App SIGABRT**。
★ 生成的 SPIR-V 本身用 `spirv-val` 验过是**合法**的，所以不是"编坏了"，
更像是 **NDK 自带 glslc（shaderc v2022.3 / 2022 年）太老**、产出的模块
Adreno 740 的驱动不接受。**这一条本轮没修好**，处理方式是第九节的"自动回落 CPU"。

十、★★ 轮次66 新增的"防闪退 + 自动回落"（**产品要求：默认开 GPU，但不支持时必须静默回落**）
--------------------------------------------------------------------------------------------

`jni/dspllm_jni.cpp` 里现在有三层：

1. **加载时探设备**：`ggml_backend_dev_count()` 数一遍 GPU（GPU||IGPU）；
   一个都没有 ⇒ 把层数压回 0，打一行 `★★ 后端设备：… ⇒ 一个 GPU 设备都没有，自动回退 CPU`。
2. **生成时兜异常**：JNI 入口 `try/catch` 包住整个生成；抓住之后
   ⇒ 打日志 ⇒ **按纯 CPU 重新加载模型** ⇒ **把这一次生成重跑一遍**。
   用户只会觉得"慢"，不会看到闪退。
3. **粘性标记** `g_gpu_runtime_failed`：炸过一次之后，本进程内后续加载一律不再试 GPU
   （否则每一句都要先炸一遍、白等一次）。

★ 另外把 `llama_log_set()` 接到 `__android_log_print`，ggml 自己的日志（含
`llama_prepare_model_devices: using device Vulkan0 (Adreno (TM) 740)`、
`load_tensors: offloaded N/M layers to GPU`）现在**能在 logcat 里看到** ——
这是"GPU 到底用没用上"在真机上唯一的可观测证据。
★ 但**必须丢掉 `GGML_LOG_LEVEL_DEBUG`**：实测把 DEBUG 也接进 logcat，
光 `llama_graph_n_input_tensors` 一次加载就几千行，会把缓冲区冲爆，
真正要看的那几行反而被冲掉（本轮第一次真机跑就是这么丢掉证据的）。

### 11.1 ★★★ 「NDK 自带 glslc 太老」这个假设 —— **实测被推翻**（轮次66 的结论是错的）

轮次66 的推断是：`createComputePipeline: ErrorUnknown` 是"NDK 自带 glslc 太老
（shaderc v2022.3 / ndk-r26c）产出的 SPIR-V 老驱动不接受"，因此想去装新版 Vulkan SDK。

**轮次67 做了对照实验，结论是这条路走不通（不是猜的，是逐字节比的）：**

| | NDK 27.2.12479018 自带 | NDK r29（29.0.14206865）自带 |
|---|---|---|
| glslc 版本串 | `shaderc v2022.3 **ndk-r26c**` | `shaderc v2022.3 **ndk-r28b**` |
| glslc.exe 字节数 | 6,432,864 | 6,332,056 |

用**同一个 llama.cpp 源码、同一个 clang 工具链**，只换 `glslc`，各编一遍
（`build/_r67/build_vulkan_r67.bat`，产物目录 `build-arm64-vk2`），
然后把两个构建目录里 **1119 个生成的 SPIR-V** 逐一对比：

```
旧（ndk-r26c）目录：1119 个文件 / 合共 25,354,464 字节
新（ndk-r28b）目录：1119 个文件 / 合共 25,354,464 字节
mul_mat_vec_q4_k_f32_f32.spv                  18844  C02ED4A1… 同
mul_mat_vec_q4_k_f32_f32_subgroup.spv         18972  4035EE73… 同
mul_mat_vec_q4_k_f32_f32_subgroup_no_shmem.spv 17320 0BF25E2C… 同
mul_mat_vec_q6_k_f32_f32.spv                  26784  25581854… 同
mul_mat_vec_q8_0_f32_f32.spv                  22828  870937C7… 同
```

⇒ ★★★ **两个 glslc 产出的 SPIR-V 逐字节相同**。所以"换个新一点的 NDK glslc"
**不可能**改变任何着色器、也就不可能修好这个驱动拒绝。
⇒ 结论：**"去装 Vulkan SDK 拿新 glslc"这条路线被证伪**，别再花时间。
（顺带实测：`sdk.lunarg.com/sdk/download/latest/windows/vulkan-sdk.exe` 在本机
**挂了约 2 小时只落盘 2,953,216 字节**（约 2.9 MB；安装器本体是几百 MB 量级），

★★ 另外一个**对得上号的巧合**（值得记住）：上面那两个数字

### 11.2 ★★★ 第三条本地补丁：Adreno matvec 兼容回退（**这条才是真修法**）

上游依据（两条都查到原文了，不是我们猜的）：
* **llama.cpp issue #28635**：同一份 GLSL、不同 shaderc/NDK 产出的 SPIR-V，
  在 Adreno 830 上 `vkCreateComputePipelines` 返回 `VK_ERROR_UNKNOWN`。
* **llama.cpp PR #29165（Adreno 750）**：subgroup 归约的 dequant `mul_mat_vec` 管线
  会把 Qualcomm 驱动的着色器编译器搞崩；PR 描述里**逐字**写着
  **「q4_K at 1 column fails pipeline creation with `VK_ERROR_UNKNOWN`」**
  —— 而**单 token decode 就是 1 列**。
* 上游的修法：在 `ggml_vk_load_shaders` 里把 `use_subgroups` 置 false，
  让 `mul_mat_vec` 退回**代码里本来就有**的 shared-memory 归约

**本工程的改法（与上游不同的地方，故意不同）：**
上游 PR 把设备名单**写死**成 `vendorID==0x5143 && driver_id==8 && driverVersion==2150604839
&& deviceName=="Adreno (TM) 750"`，还默认 OFF。本工程要通吃所有手机 GPU，
写死型号等于换台机器就失效 ⇒ 改成 **只按厂商判**：
`device->properties.vendorID == 0x5143u`（Qualcomm）就关掉 subgroup 归约。

位置：`ggml/src/ggml-vulkan/ggml-vulkan.cpp` 的 `ggml_vk_load_shaders()` 开头，
原 `const bool use_subgroups = device->subgroup_arithmetic;` 改成 `bool` 并加：
```cpp

        const char * dsp_env = getenv("GGML_VK_ADRENO_SUBGROUP");
        const bool dsp_force = (dsp_env != nullptr && dsp_env[0] == '1');
        GGML_LOG_INFO("ggml_vulkan: Adreno 检测到（vendor=0x%04x driver_id=%u driver_version=%u subgroup=%u）"
```

★ **留了 A/B 开关**（`GGML_VK_ADRENO_SUBGROUP=1` 强制保留 subgroup 归约）：
改完必须还能在**同一台机器上**做对照，否则"修好了"没法证明。
★ JNI 侧把**系统属性**桥接成这个环境变量（`jni/dspllm_jni.cpp`）：
```

adb shell setprop debug.dsp.adreno_subgroup 0   # 走回退（= 轮次67 默认）
```

⇒ 改属性之后要让 App **重新起一个进程**（`am force-stop` 再打开，不丢数据）才保证生效。

### 12.4 ★★ 本轮踩到的两个坑（都值得记）

**坑 ①（纪律级）：绝不在**编译**的同时跑反向套件。**
反向套件的破坏项会**临时改写** `jni/dspllm_jni.cpp` 等源文件，
而 ninja 那一刻正好在读这些文件 ⇒ `os.replace()` 还原时抛
`PermissionError: [WinError 5] 拒绝访问`，脚本**当场中断**，
留下一个 `.r66bak` 与被改坏的源文件（本轮实测发生）。处理：
`recover()`（脚本开头的那个函数）会把 `.r66bak` 还原；
本轮实测还原后源文件与原文一致（74,786 字节），并把 `dspllm_jni.cpp.o` **删掉重编**，
再用字符串检查确认 `.so` 里是**新**文案而不是被破坏的中间态。
⇒ **规矩：重编与反向套件分两个时间窗跑。**

**坑 ②：`ninja` 只看时间戳，"源文件被改回来"它会当成"没变"。**
上面那次事故之后，`.o` 比 `.cpp` **新**（虽然它是从被改坏的中间态编出来的）
⇒ `cmake --build` 只做了一次 Linking（`[1/1]`），**没有重编**。
识别方法：正常重编的第一行一定是 `[1/2] Building CXX object ... dspllm_jni.cpp.o`；
只看到 `[1/1] Linking` 就说明它**没**重编 ⇒ 手动删 `.o` 再来一遍。

十三、★★★ 轮次69：两态（开 / 关）+ **删掉那个把"换模型"堵死的粘性标记**（**照这一节做**）

### 13.1 这一轮改了什么（**只有 JNI**，llama.cpp 一行没动）

用户原话：「**增加模型卸载功能，现在安装了之后模型无法更换其他的gguf模型，
然后吧加速做成开GPU**」。⇒ 本轮 = **修 bug + 简化设置**。

* `jni/dspllm_jni.cpp`：
  * 宏改成**两个**：`#define DSP_GPU_MODE_OFF 0` / `#define DSP_GPU_MODE_ON 1`
    （轮次68 的 `_AUTO(1)` / `_FORCE(2)` **删掉**；Java 侧不再可能传 2，
    传进来也会被 `normalize_gpu_mode` 当成认不出 ⇒ off，落在安全的一侧）；
  * `do_load_locked()` 里**两态分流**：`on` 探不到 GPU ⇒ `set_err("开 GPU 失败…")` + `return false`
    （**不压回 0 层**）；`off` 才 `want_gpu = 0`（并且显式只把 CPU 设备交给 llama.cpp）；
  * ★★★ **删掉进程级粘性标记 `g_gpu_runtime_failed`**（轮次66 引入、轮次68 只让它对 auto 生效）：
    它就是用户报的"换不了模型"的根因 —— 默认 force 之下，一次 GPU 失败之后
    `do_load_locked` 里那条 `if (g_gpu_runtime_failed) { set_err(...); return false; }`
    会让**之后每一次加载**（换模型、重新导入都算）直接失败，只有"用户手动改一次 GPU 方式"才能清掉。
    ⇒ 现在**每次加载都是一次全新的尝试**。该标识符在本文件的**真代码里出现 0 次**（断言钉着；
    注释里还留着它的名字讲这段历史，`cpp_code`（去注释视图）里查的是"0 次"）；

### 16.8 ★★★ 轮次72 收尾：真机上抓到的**两个报告缺陷**（都已修 · 反向项 CU~DB 钉着）

★ 这一节是**收尾轮**补的：16.2 那张读数表是用**旧报告格式**跑出来的，而旧格式本身有两个缺陷。

1. ★★★ **`-1`（"这一步没跑到"的哨兵）被当数字印**。失败档的报告里原本是：
   ```
   prefill=8 tok / -1 ms (0.00 tok/s)
   decode=0 tok / -1 ms (0.00 tok/s, -1 ms/token)
   ```

15.1 第四条本地补丁（`ggml/src/ggml-vulkan/ggml-vulkan.cpp`）
------------------------------------------------------------------
在 `ggml_vk_get_dequantize_mul_mat_vec()` 的 workgroup 启发式之后加：

    if (getenv("GGML_VK_ADRENO_HYBRID") != nullptr && ctx->device->vendor_id == 0x5143u) {
        dmmv_wg = DMMV_WG_SIZE_LARGE;
        GGML_LOG_INFO("ggml_vulkan: Adreno HYBRID 生效：dmmv_wg=LARGE（a_type=%d m=%u k=%u）"
                      " ⇒ 期望归约模式 = HYBRID（_subgroup_no_shmem）\n", (int) a_type, m, k);
    }

**为什么**：q4_K matvec 有三条 SPIR-V 变体（`arr_dmmv_q4_k_f32_f32[3]`）：
`reduc16 = (use_subgroups16 && w == SUBGROUP) ? SUBGROUP
         : (use_subgroups16 && w == LARGE)    ? HYBRID : SHMEM`
而 `dmmv_wg` 在 Qualcomm 上**永远是 SUBGROUP**（上游只给 NVIDIA/Intel 选 LARGE）
⇒ **HYBRID（`_subgroup_no_shmem`）在 Adreno 上从来没被选到过**。
轮次72 只测了 SHMEM 与 SUBGROUP（都失败）⇒ 第三条是唯一没试过的。
★ 变量没设时行为与上游**逐字相同**（默认路径零影响）。

另外在 `ggml_vk_load_shaders()` 里 `use_subgroups16` 定义之后加了一行**诊断日志**
（`Adreno HYBRID 检查：use_subgroups=… ⇒ use_subgroups16=…`）——
因为三条变体的 `pipeline->name` 完全相同，日志里不打出选了哪一档，
"第三档试过了"就只是说法、不是证据。

15.2 ★★★ 重编 ggml-vulkan 时**必须**加这个 include（本轮踩到的坑）
------------------------------------------------------------------
`build-arm64-vk2` 这个 build 目录的 `Vulkan_INCLUDE_DIR` 指向 NDK sysroot，
而 sysroot 里**只有 `vulkan.h`、没有 `vulkan.hpp` 与 `spirv/unified1/spirv.hpp`**
⇒ 直接 `cmake --build` 会报 `fatal error: 'vulkan/vulkan.hpp' file not found`。
两个头文件包都在本机（`D:\vk_headers`、`D:\spirv_headers`），
`D:\spirv_headers\install\include` 里**同时**有 `vulkan/` 与 `spirv/`。做法：

    set PATH=D:\Android\Sdk\cmake\3.31.6\bin;%PATH%
    cmake -S D:\llamacpp_src\llama.cpp-b76b13379d3b7d67ab0bc424516bb6fd2522bd8e ^
          -B D:\llamacpp_src\build-arm64-vk2 ^
          "-DCMAKE_CXX_FLAGS=-isystem D:/spirv_headers/install/include"
    cmake --build D:\llamacpp_src\build-arm64-vk2 --target ggml-vulkan --parallel 12

★ 用 `-DVulkan_INCLUDE_DIR=…` **不行**：重新 configure 时 `find_package(Vulkan)` 会把它
改回 sysroot（本轮实测两次），必须走 `CMAKE_CXX_FLAGS`。
然后 strip 再拷进工程（否则 APK 里是 31.8 MB 的未 strip 版）：

    D:\Android\Sdk\ndk\27.2.12479018\toolchains\llvm\prebuilt\windows-x86_64\bin\llvm-strip.exe ^
        --strip-unneeded D:\petbuild\lib\arm64-v8a\libggml-vulkan.so

================================================================================================
十六、轮次74：**运行时自动检测硬件 → 动态算 n-gpu-layers → 自动降级**
================================================================================================

★ 这一轮**没有改 llama.cpp**（第四条本地补丁原样保留）；改的是 JNI + Java。
★ 用户原话：「核心思路：运行时自动检测硬件 → 动态计算 -(n-gpu-layers)
→ 自动降级兜底不用用户手动调参数。」

16.1 JNI 新增：`nativeDeviceInfo()`（两套包名都有）
------------------------------------------------------------------
`device_info_text()`（`dspllm_jni.cpp`，紧挨着 `g_backend_inited`）：

* 第一次调用时 `llama_backend_init()`（与 `do_load_locked` 同一个入口，只做一次），
  然后 `ggml_backend_dev_count()` 枚举设备，取第一个 GPU/IGPU 的
  **description**（`Adreno (TM) 830`；`name` 是后端名 `Vulkan0`，不是机型）
  与 `ggml_backend_dev_memory()` 的 free/total；
* 返回一行自描述串：
  `vulkan=1;count=1;name=Adreno (TM) 830;backend=Vulkan0;vram_free=15252;vram_total=15252;subgroup=0`
* ★★ **调用方必须是后台线程**（Vulkan 枚举在部分机型上要几十~几百毫秒）；
* ★ 少一套包名的转发 ⇒ 正式版的"自动"永远以为没有 GPU（直接纯 CPU，不报错）。

16.2 Java 侧新增
------------------------------------------------------------------
* `GpuPlan.java`（**纯类**，零 Android 依赖）：`decide(Facts)` → `Plan`；
  `degrade(Plan)`；`looksLikeGpuFailure(String)`；`summary` / `reportLines`。
  规则：没有 Vulkan ⇒ CPU；已知坏机型（Adreno 830，实测）⇒ CPU；
  否则 `每层 = modelBytes / layers`、`预算 = availRam × 55%（≤3072 MB）`、
  `ngl = 预算 / 每层`；放得下 1/3 以上才用 GPU（部分卸载往往更慢）。
* `LocalHardware.java`：取数 + 缓存（`LocalLlm.deviceInfo()` / ActivityManager / `ModelFile.ggufLayerCount`）。
* `ModelFile.ggufLayerCount(byte[] / File)`：只读 GGUF **前 64 KB**，扫 `<arch>.block_count`；
  读不到返回 0（调用方必须当"不知道"，用 `EST_LAYERS=32` 估算并标 `estLayers`）。
* `GpuMode`：加回 `AUTO` 并设为默认；`allowCpuFallback(auto)=true`，`on/off=false`。
* `LocalChat`：`loadPlanned()` 统一载入（计划 → load → 自动档失败则降级重载一次）；
  `reloadCpu()` 给**生成阶段**的降级用（真机上 GPU 就炸在建计算管线）；
  降级原因记进 `LocalHardware.noteFallback()`（面板 + 自检报告都能看见）。
* `LocalSelfTest.compose(..., autoLines)`：报告多两行 `自动计划=` / `硬件=`。

16.4 诚实边界
------------------------------------------------------------------
* 已知坏机型名单**只有 Adreno 830**（轮次72/73 实测）；别的机型会**先试** GPU，失败再降级。
  这不是"所有 Adreno 都不行"；
* 层数靠 GGUF 头读；读不到就是**估算**（32 层）—— 报告里标 `（估算）`，不许装成读到了；
* 降级只降**一次**（GPU → CPU），不会来回弹；
* 「开」是手动对照档：失败**不降级**（否则 A/B 就没法做）；
* 真机验收（自动档 → 纯 CPU + 硬件探测日志）在 `build/_r74/`（★ 那一轮设备**反复掉线**，
  若 `ab74_results.txt` 缺失 = 没跑成，别把"没跑"读成"跑过了"）。
